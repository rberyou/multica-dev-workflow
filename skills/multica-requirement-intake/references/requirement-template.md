# 顶层需求模板

## 模板

```markdown
# <简洁、结果导向的标题>

## 背景

说明用户场景、业务目的和问题发生的上下文。

## 问题描述

说明当前行为、期望行为以及两者之间的差异。只写已知事实；推测应明确标记。

## 复现与证据

1. 前置条件
2. 操作步骤
3. 实际结果
4. 出现频率

附上脱敏日志、错误样例、截图、输入输出或相关链接。

## 目标

说明需求完成后应达到的用户或系统结果，不在这里批准具体实现方案。

## 验收条件

- [ ] <可观察、可测试的结果 1>
- [ ] <可观察、可测试的结果 2>
- [ ] <关键失败路径得到处理>
- [ ] <现有兼容行为没有回归>

## 范围

- <明确包含的模块、流程或平台>

## 非目标

- <本次明确不处理的内容>

## 约束与风险

- <兼容性、性能、安全、隐私、迁移或发布约束>

## 待 Plan 阶段确认

- <需要方案阶段调查或决定的问题>

## 关联信息

- 项目/仓库：<名称或 URL>
- 环境/版本：<如适用>
- 相关 issue/PR：<如适用>
- 创建来源：Codex / OpenCode / 人工
```

## 编写规则

- 标题描述问题或结果，不写“修改一下”“优化代码”之类模糊动作。
- 验收条件必须能由测试、日志、界面行为或接口结果验证。
- 把实现建议放入“待 Plan 阶段确认”，并标记为候选方案，不能写成已批准设计。
- 不预先创建任务列表。任务 DAG 由 Plan 的任务拆分阶段生成。
- 不写 `human_approver_id`。人工审批人由队长从 roster 自动识别。
- 不把 Token、密码、私钥或未脱敏的生产数据放入 issue。

## AINotes 示例

```markdown
# AINotes 复习题干生成应能稳定处理 LLM 非法 JSON

## 背景

AINotes 在复习流程中调用 LLM 生成题干，并把返回内容解析为结构化数据。当前解析稳定性会直接影响复习能否继续。

## 问题描述

LLM 偶尔返回不符合预期格式的 JSON，例如附带 Markdown code fence、字段缺失、字符串转义错误或正文前后存在额外文本。当前流程在这些情况下直接失败，导致用户无法继续复习。

## 复现与证据

1. 进入包含可复习知识点的笔记。
2. 启动复习并触发题干生成。
3. 当模型返回非法 JSON 时观察解析失败。
4. 保存脱敏后的原始模型输出、解析错误和模型信息用于定位。

该问题为间歇性发生，具体频率需要在 Plan 阶段通过日志确认。

## 目标

题干生成流程能够可靠处理常见的 LLM 输出偏差；无法恢复时向用户提供可理解、可重试的错误，并保留足够的脱敏诊断信息。

## 验收条件

- [ ] 合法 JSON 的现有生成流程保持正常。
- [ ] 针对已收集的常见非法输出样例有自动化测试。
- [ ] 可安全恢复的格式偏差不会中断复习流程。
- [ ] 无法恢复的返回会产生明确错误并允许重试，不会静默生成错误题目。
- [ ] 诊断记录可关联请求和解析阶段，且不泄露敏感笔记内容。
- [ ] 解析或重试策略不会造成无上限调用或重复计费。

## 范围

- 复习题干生成的 LLM 返回解析、校验、错误处理、重试和相关测试。

## 非目标

- 更换整个 LLM 提供商。
- 重做复习 UI 或间隔重复算法。
- 在未评估成本和兼容性的情况下改变公共数据格式。

## 约束与风险

- 必须区分“可修复格式问题”和“语义不可信内容”。
- 原始输出的记录必须脱敏并遵守现有日志策略。
- 重试次数、模型调用成本和延迟需要有明确上限。

## 待 Plan 阶段确认

- 根因主要来自提示词、模型输出约束、解析器容错还是多项组合。
- 是否使用结构化输出能力、schema 校验、有限修复或重新请求。
- 原始输出采集的范围、保留期限和脱敏方式。
```

## 常用提示词

直接提交：

```text
使用 multica-requirement-intake，把以下问题整理成顶层需求并提交到 Multica 的 AINotes 项目，分配给开发交付小队并启动：<问题详情>
```

只生成草稿：

```text
使用 multica-requirement-intake，按顶层需求模板整理以下内容，不要创建 issue：<内容>
```

查看进度：

```text
使用 multica-requirement-intake 检查 T-123 的完整 issue 链和最新评论，只告诉我当前阶段、阻塞原因、我需要做的操作和下一步，不要修改任何内容。
```
