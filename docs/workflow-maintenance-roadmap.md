# 工作流维护小队开发路线图

- 路线图版本：`0.3.2`
- 状态：设计基线草案
- 范围：Observer、Maintainer、Reviewer

本文档定义工作流维护小队的设计目标、总体架构和分阶段建设方向。具体接口、数据结构、状态字段和实现方案应在各阶段的独立设计中确定。

## 1. 设计目标

工作流维护小队负责持续发现并修复本仓库开发工作流中的缺陷。

人工保留以下决策权：

1. 是否对已确认的问题启动维护。
2. 是否批准发布和部署。

获得人工授权后，小队自动完成问题分析、维护方案、代码实现、测试、独立审查、合并、发布准备、Canary、部署验证和批准范围内的回滚。

目标是让人工成为决策者，而不是流程操作员。正常维护过程中，不应要求人工修改 Issue、调整状态、重新指派任务或执行常规命令。

## 2. 总体架构

```text
开发小队 Agent 主动上报 ──┐
                          ├──> Observer ──> Incident ──> 人工决定是否维护
定时巡检 ────────────────┘                              │
                                                       ▼
                                               Maintenance Case
                                                       │
                                      Maintainer <──> Reviewer
                                                       │
                                                       ▼
                                              审查通过并完成合并
                                                       │
                                                       ▼
                                                人工批准发布/部署
                                                       │
                                                       ▼
                                      Maintainer 执行，Observer 验证
```

工作流维护小队独立于开发小队。开发小队负责业务交付，只向 Observer 报告工作流异常；维护小队只维护本仓库的工作流产品，不参与普通项目功能开发。

一个工作流缺陷对应一个 Incident 和一个 Maintenance Case。维护过程中的方案、实现、审查、发布和验证作为同一 Case 的阶段和证据管理，不为每个阶段创建独立 Issue。

对象归属保持明确：Observer 负责 Incident，Maintainer 负责 Maintenance Case，Reviewer 只负责审查结论，人工批准作为不可由 Agent 代写的独立证据。`DECISION_REQUIRED` 表示现有维护授权不足或风险发生变化，需要人工重新决策，不属于常规流程门禁。

## 3. 成员定位与职责

### Observer — 发现与验证

**定位：** 独立的工作流观察者、问题入口和最终验证者。

**职责：**

- 接收开发小队 Agent 主动上报的工作流异常。
- 巡检已登记使用开发小队的项目及其工作流运行记录。
- 发现无人主动报告的配置漂移、任务停滞、门禁异常和运行故障。
- 对报告和巡检结果进行分类、去重并记录 Incident。
- 向人工请求是否启动维护的决策。
- 验证 Canary、部署、回滚和最终修复结果，并关闭已解决 Incident。

**边界：** 不修改工作流源码，不制定修复方案，不执行发布或部署，不启动未经人工批准的维护。

### Maintainer — 维护执行者

**定位：** 人工批准维护后，负责完成整个修复过程的执行者。

**职责：**

- 分析 Incident，确定根因和影响范围。
- 编写维护方案并实现代码修改。
- 运行测试、准备 PR，并与 Reviewer 自动完成审查修改循环。
- 在审查和 CI 通过后完成合并。
- 准备发布、Canary、部署和回滚方案。
- 在人工批准发布或部署后执行对应操作。
- 将执行结果交给 Observer 验证。

**边界：** 不能审查自己，不能伪造人工批准，不能扩大已批准的维护范围，不能绕过失败门禁。

### Reviewer — 独立审查者

**定位：** 独立于 Maintainer 的质量和风险门禁。

**职责：**

- 审查问题分析、维护方案、代码、测试和兼容性。
- 审查发布、Canary、部署和回滚证据。
- 提出修改意见并自动退回 Maintainer。
- 在内容满足要求时给出批准结论。
- 遇到范围、风险或产品决策时请求人工判断。

**边界：** 不修改被审查内容，不执行合并、发布、部署或回滚，不代替人工作出维护和发布决策。

## 4. 发现机制

Observer 通过两条路径发现问题：

- **主动上报：** 开发小队 Agent 在执行开发工作流时发现异常，向 Observer 提交来源、现象和必要证据。
- **主动巡检：** Observer 定时检查已登记项目中由开发工作流创建或管理的 Issue、Agent 任务和控制面状态。

项目必须在启用开发小队时显式登记。工作流创建的 Issue 必须携带可识别的来源标记，使 Observer 能确定巡检范围，并发现缺少标记的孤立记录。

Observer 应保证重复报告和重复巡检最终汇聚到同一个 Incident；扫描失败后能够从已记录进度继续，而不是遗漏或重复创建问题。

## 5. 权限架构原则

三名 Agent 必须具有独立权限边界，权限限制不能只依赖提示词。

- Observer 只拥有巡检、Incident 记录和验证所需权限。
- Maintainer 只拥有隔离开发环境和经过批准的执行权限。
- Reviewer 只拥有读取被审查内容和提交审查结论的权限。
- Agent 不直接持有宿主机或人工审批凭据。
- 合并、发布、部署和回滚等操作必须受到身份、范围和批准证据约束。
- 所有重要决策、审查和外部操作必须保留可追溯证据。

## 6. 三阶段开发路线

### 第一阶段：异常上报与 Observer 闭环

详细设计见 [工作流维护第一阶段详细设计](workflow-maintenance-phase1-design.md)。

目标是让开发小队 Agent 能够正常上报工作流异常，并让 Observer 独立完成发现、分类、去重、记录和验证职责。

阶段成果：

- 开发 Agent 可以通过统一方式主动上报异常，并附带来源和必要证据。
- Observer 可以识别开发小队运行的项目和工作流 Issue。
- Observer 可以定时巡检、接收上报、分类 finding 并去重。
- Observer 可以创建或更新唯一 Incident，并记录巡检进度。
- Observer 可以向人工请求是否启动维护的决策。
- 人工批准后创建与 Incident 关联的最小 Maintenance Case，供现有普通开发流程跟踪修复。
- Observer 可以验证已完成修复的结果并关闭 Incident。

第一阶段不启用 Maintainer 自动修复，也不要求完整生产级安全隔离。人工批准维护后，现有普通开发流程暂时代行 Maintenance Case 的执行，Observer 只负责持续跟踪和最终验证；这是阶段性替代，不改变 Maintainer 在目标架构中的最终归属。重点是证明异常能够被可靠发现、记录、跟踪和验证。

当前仓库 `workflow.phase=1`。因此 `workflow.json`、Observer 控制面契约、默认 Skill 安装、常规 CI 和发布资产都只包含普通开发流程与 Observer 所需组件；Maintainer、Maintenance Reviewer 和 Secure Runtime 仅保留为未来阶段源码，其验证必须放在独立的未来组件变更中。

### 第二阶段：维护闭环

目标是让 Maintainer 和 Reviewer 在人工批准维护后，自动完成从问题分析到发布准备的完整维护流程。

阶段成果：

- 人工只需决定是否维护一个已确认 Incident。
- Maintainer 可以自动完成分析、方案、实现、测试和 PR 准备。
- Reviewer 可以独立审查，并将普通修改意见自动退回 Maintainer。
- Maintainer 和 Reviewer 可以自主完成修改与复审循环。
- 审查和 CI 通过后可以在受控测试环境中完成合并流程并准备发布。
- 整个过程使用一个 Maintenance Case 管理，不产生复杂的阶段 Issue 树。
- 真实仓库合并、发布、Canary、部署和回滚仍由人工执行；Agent 负责生成完整、可验证的操作计划和证据。

第二阶段重点验证维护业务闭环，不向尚未完成硬隔离的 Agent 开放真实外部变更权限。

### 第三阶段：安全隔离与生产化

目标是让维护小队能够在真实环境中长期、安全、自主运行。

阶段成果：

- Observer、Maintainer 和 Reviewer 使用相互独立的硬权限环境。
- 权限、凭据和外部操作由受控能力接口管理，而不是依赖 Agent 自律。
- 人工批准后，Maintainer 可以自动执行发布、Canary、部署和回滚。
- Observer 可以持续巡检并独立验证修复效果。
- 越权操作、伪造批准、自我审查和范围扩张在技术上无法执行。
- 完整流程通过真实 Canary、权限负向测试和回滚演练。

## 7. 完成标准

工作流维护小队达到最终目标时，应满足：

- 一次人工维护决策后，任务可自动运行到发布或部署审批点。
- 一次人工发布或部署批准后，Agent 可完成后续执行和验证。
- 正常流程不需要人工维护 Issue 状态或执行常规命令。
- 重复报告与巡检不会产生重复 Incident。
- 三名 Agent 的职责和权限在技术上相互隔离。
- 发生异常时能够自动重试、回滚或明确请求人工决策。
